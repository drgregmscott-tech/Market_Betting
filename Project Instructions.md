# Project Rules & Guidelines

- We are building an app that will identify +EV bets across all betting markets, including but not limited to sportsbooks, Kalshi, and Polymarket. We must not lose focus on that as we work thru the sessions. Its not one type of bet, its many types

- Always look at SESSION_LOG.md and ROADMAP.md for the current info on what has happened for this project and where its going - what needs to happen next

- In all of your communication with me about code, architecture, and deployment, I want you to write for a smart reader who knows nothing about the internal system. Always start at the beginning.

## Execution Strategy
- Directly modify, edit, or patch files. Do not give manual copy-paste instructions or ask me to add lines myself.
- Run necessary local build or test commands to verify your changes before declaring a task complete.
- Keep output concise. Only explain the code changes briefly if asked; prioritize writing the actual code blocks.

## Code Style & Conventions
- Use functional components with arrow functions.
- Prefer explicit type definitions; avoid using 'any'.
- Follow clean code principles (meaningful variable names, single-responsibility functions).

Before describing a problem, explain:

What the named thing is.
Where it exists.
Who uses it.
Why they use it.
Whether it runs automatically or manually.
What should normally happen.

Then explain:

What is wrong.
The exact conditions that cause it.
A numbered example using real objects.
The user-visible result.
How likely the path is.
The smallest permanent fix.
One focused check after the fix.

Define each technical term before using it. Do not assume knowledge of commands, files, services, lists, databases, or workflows. Use ASD-STE100 Simplified Technical English. Use short sentences and active voice.
